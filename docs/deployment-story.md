# DGX Spark 本地大模型部署实录（大白话版）

> 这篇文章记录了一台 NVIDIA DGX Spark 上从零部署本地大模型的完整过程：装了什么、为什么这么配、实测多少速度、踩了哪些坑。
> 所有 IP、主机名、密钥、密码已替换为占位符。命令可以直接照抄，把占位符换成你自己的值即可。

---

## 0. 一句话结论

这台机器（DGX Spark，128GB 统一内存）**能流畅跑 270 亿参数的大模型**：

- **单个人用**：代码类任务 **43 tok/s**，数学类 **51 tok/s** —— 比人读得快得多，体感接近在线服务
- **多人同时用**：8 个人并发时合计 **158 tok/s**
- **上下文**：可以开到 **51 万 token**（约等于一次性读完三本《三体》）
- **代价**：单流速度比云端 API 慢，但**不花一分钱**，数据不出内网

一句话：**适合当"第二台免费的推理机"，不适合当唯一的、扛全公司流量的主力**。

## 1. 这台机器什么水平

| 项目 | 值 | 通俗解释 |
|---|---|---|
| 机器 | NVIDIA DGX Spark（GB10 芯片） | 一个巴掌大的小盒子，ARM 架构 |
| 内存 | 121.6 GiB **统一内存** | CPU 和 GPU 共用一块内存，不像普通显卡那样分家 |
| 内存带宽 | 273 GB/s | **这个数字最关键**，决定了生成速度的上限 |
| 系统 | Ubuntu 24.04.5（DGX OS） | |
| 驱动 / CUDA | 580.173.02 / CUDA 13.0 | |
| Docker | 29.2.1 + NVIDIA Container Toolkit 1.20.0 | 模型跑在容器里 |
| 磁盘 | 916 GB（NVMe） | 权重 + 缓存大约占 200–250 GB |

### ⚠️ 一个必须先建立的概念：**带宽才是速度的瓶颈，不是算力**

很多宣传会说"这台机器有 1 PFLOP 的 AI 算力"。但**生成文字（解码）这个动作，瓶颈是内存带宽，不是算力**。

打个比方：

> 生成每一个字，模型都要把**全部权重**从内存里"读一遍"。就像做菜——不是厨师刀工不够快，而是**食材从冰箱搬到案板的速度**有限。
> 所以想提速，方向是"让每搬一次能多出几个字"（投机解码），而不是"换个更快的厨师"（更强的算力）。

这个道理后面反复用到，是理解所有调优取舍的钥匙。

## 2. 部署全流程（按时间顺序）

### 阶段一：先部署了 176B 的大模型（后来换掉了）

最初的目标是 **Qwen3.8-Flash-Next 176B MoE**（一个 1760 亿参数、但每次只用 60 亿的"稀疏"模型）。选它是因为参数量大、能力强。

**第一步就卡住了：下载太慢。**

实测三条链路的真实速度：

| 下载源 | 实测速度 | 下载 135 GB 需要 |
|---|---|---|
| HuggingFace 直连 | 12.5 MB/s | **约 3 小时** |
| hf-mirror.com 镜像 | 12.5 MB/s | 约 3 小时 |
| **ModelScope（魔搭）** | **40+ MB/s** | **约 1 小时** |

于是写了一个下载脚本 `seed_hf_cache.py`，做了一件关键的事：

> **从快的源（ModelScope）下载，但用慢的源（HuggingFace）的哈希值逐个文件校验。**

这样既拿到了速度，又保证了**内容和官方发布的完全一致**——传输通道可以换，内容一字节都不能变。

结果：419 个文件、135.3 GB，全部校验通过（其中 1 个文件因为网络中断失败了一次，重试成功）。

**第二步：确认"预下载能不能被推理引擎认出来"。**

模型跑在 SGLang 引擎里，它会去 HuggingFace 的缓存目录找权重。我们手动放进去的文件，它会不会假装没看见、重新下一遍？

直接读引擎源码确认：`huggingface_hub 1.30.0` 的判定逻辑是 **"只要软链接指针存在就算命中"**，不再比对哈希。实测 `snapshot_download` **0.9 秒解析完 419 个文件、零下载**。搞定。

**第三步：安装与首次启动。**

- 安装耗时：**6.7 分钟**
- 首次启动：**10.3 分钟**（要写 47.7 GB 的 PLE 表 + 编译 CUDA 图）

**实测性能：**

| 负载 | 速度 |
|---|---|
| 代码生成 | 36.5 tok/s |
| 数学推理 | 44.6 tok/s |
| 技术说明文 | 22.1 tok/s |
| 4 人并发合计 | 68.3 tok/s |

**第四步：想再快一点，结果撞上一堵硬墙。**

这个模型用的是 **QSA 稀疏注意力**，引擎对"投机解码"参数有**硬性限制**。我们试了三种改法，全部被引擎拒绝：

| 尝试 | 引擎的报错（原文） |
|---|---|
| 把 draft 深度加到 6 | `Qwen QSA requires speculative_num_draft_tokens <= the QSA compress ratio (4): the pending index-key ring holds one group; got 6` |
| 把 steps 加到 4 | 同上，`got 5` |
| 把 topk 改成 2 | `Qwen4-Exp QSA MTP currently supports speculative_eagle_topk=1` |

**结论：这个模型的投机解码参数空间被锁死在唯一一个合法点，没有任何调优余地。** 这是引擎作者的架构决定，不是我们没调好。

> 💡 **这里有个非常阴险的坑**（后面运维章节再强调）：这些非法参数**不会在启动时报错**，而是在**权重加载完成约 10 分钟后**才抛异常。而 systemd 配了 `Restart=always`，于是变成**每 10 分钟一轮的崩溃重启循环**。我们因此白烧了约 40 分钟。

### 阶段二：换成 27B 模型（现在跑的就是它）

176B 虽然强，但每次只能用 4 路并发（QSA 的限制），而且占 203 GB 磁盘。换成 **Qwen3.8-27B-NVFP4** 后：

- 显存占用从 176 GB 降到 25 GB
- 并发上限从 4 提到 8
- **单流速度反而更快**（模型小 = 带宽压力小）

**卸载旧模型**：

⚠️ 注意：卸载脚本**只删服务配置，从不删数据**（权重、镜像、缓存表都不会动），它会**打印**回收命令让你自己执行。这是好设计，但你要知道。

实际回收：**203 GB**（权重 126 GB + 缓存表 48 GB + 镜像 30 GB），磁盘从 243 GB 已用降到 **40 GB**。

**部署新模型**：权重 21.9 GB + 投机草稿模型 3.85 GB，同样用 ModelScope + 哈希校验的方式预置，安装时下载步骤**秒过**。

**实测性能（对比 176B）：**

| 负载 | 176B | **27B** |
|---|---|---|
| 代码 | 36.5 | **43.2** ⬆ |
| 数学 | 44.6 | **51.3** ⬆ |
| 4 人并发 | 68.3 | 62.8 |
| 8 人并发 | —— | **157.7** ⬆⬆ |

**并发提升非常明显**——因为 27B 没有 QSA 那个限制，能真正跑满 8 路。

### 阶段三：上下文扩容（26 万 → 100 万 → 最终 51 万）

模型原生支持 26 万 token 上下文。但实际使用中发现：**一个跑久了的长会话会超过这个数**，导致切换模型时报错 `CONTEXT_WINDOW_EXCEEDED`。

于是用 **YaRN 技术**（一种"位置编码外推"方法）把窗口扩到 **100 万 token**。做法是修改模型的 `config.json`：

```
max_position_embeddings: 1010000     # 最大位置
rope_type: yarn                       # 启用 YaRN 外推
factor: 4.0                           # 外推倍数（262144 × 4 ≈ 100 万）
original_max_position_embeddings: 262144
```

⚠️ **目标模型和草稿模型都要改**，只改一个会导致草稿模型加载时崩溃。

**但后来又主动降回 51 万**，原因是内存：

| 配置 | 上下文 | KV 缓存池 | **系统可用内存** |
|---|---|---|---|
| 原生 | 262,144 | 46 万 token | 45.0 GiB |
| YaRN 1M | 1,010,000 | 101 万 token | **17.7 GiB** ⚠️ |
| **YaRN 512K（当前）** | **524,288** | **72.8 万 token** | **33.2 GiB** ✅ |

100 万上下文时系统只剩 17.7 GiB 可用内存，太紧张（引擎文档警告过：统一内存紧张时**整机会被拖死，需要断电重启**）。降到 51 万后内存回到 33.2 GiB，是速度和安全的平衡点。

**最终配置：**

```
--context-length 524288            # 51 万 token 上下文
--mem-fraction-static 0.60         # 内存分配比例
--max-running-requests 8           # 最多 8 个请求同时处理
--speculative-num-draft-tokens 8   # 投机解码草稿长度
```

## 3. 实测报告（完整数据）

### 3.1 单流速度（一个人用）

| 负载类型 | 速度 | 说明 |
|---|---|---|
| 代码生成 | **43.2 tok/s** | |
| 数学推理 | **51.3 tok/s** | 最快，因为数字推理可预测性高 |
| 技术说明文 | 22.1 tok/s | |
| 自由散文（中/英/法/德） | 15.6–20.6 tok/s | 最慢 |

**为什么差这么多？** 因为用了**投机解码**：引擎先"猜"接下来几个字，再一次性验证。

> 就像打字时的输入法联想——**代码和数学很规整，猜得准**（一次能猜中 5–6 个字）；**散文天马行空，猜不准**（只能猜中 1–2 个）。
> 实测接受长度：代码类 5.0–6.2，散文类掉到 1.2–1.9。

### 3.2 并发速度（多人同时用）

| 并发数 | 合计速度 | 首字等待 |
|---|---|---|
| 4 人 | 62.8 tok/s | — |
| **8 人** | **157.7 tok/s** | 0.48 秒 |
| 16 人 | 161.4 tok/s | **7.6 秒** ⚠️ |
| 32 人 | 176.2 tok/s | **25.6 秒** ⚠️ |

**这张表非常重要，揭示了两个事实：**

1. **8 路以上再多人也不明显变快**（158 → 176，只涨 12%），因为引擎配置里写死了"同时最多处理 8 个请求"，多出来的在排队。
2. **但排队会让首字等待急剧恶化**：从 0.48 秒涨到 **25.6 秒，慢了 50 倍**。

> **实践建议**：对外提供服务时，把并发控制在 8 左右。超过就是"大家一起等"，体验更差。

### 3.3 稳定性测试

跑了 8 路并发 × 10 轮的持续压测（约 3.5 分钟）：

| 指标 | 结果 |
|---|---|
| 错误数 | **0** |
| 速度波动 | 143.5 – 168.4 tok/s（均值 157.7） |
| **内存漂移** | **全程恒定 45.0 GiB，无泄漏** ✅ |

### 3.4 长文本能力

| 输入长度 | 首字等待 | 生成速度 | 能否准确检索到埋在中间的信息 |
|---|---|---|---|
| 2.5 万 token | 15.6 秒 | 26.7 tok/s | ✅ 命中 |
| 8.4 万 token | 65.6 秒 | 18.2 tok/s | ✅ 命中 |
| 34 万 token（1M 模式时测） | 649.9 秒 | — | ✅ 成功处理 |

**注意**：**长文本的瓶颈在"读"（首字等待），不在"写"**。8.4 万 token 要等 65 秒才吐出第一个字。这是物理限制（要把这么多内容全部过一遍模型）。

### 3.5 资源占用

| 项目 | 数值 |
|---|---|
| 模型权重（GPU） | 74.9 GiB |
| 其中 KV 缓存池 | 72.8 万 token |
| 系统可用内存 | 33.2 GiB |
| **KV 缓存峰值使用率** | **仅 18%** |

最后一行很重要，第 5 章会用到。

## 4. 各项参数为什么是这些值

| 参数 | 值 | 为什么 |
|---|---|---|
| `--mem-fraction-static` | 0.60 | 决定给"权重 + KV 缓存"分多少内存。**调太高会拖死整机**，0.60 是当前上下文长度的平衡点 |
| `--context-length` | 524288 | 上下文窗口。越大越吃内存，见第 3 章的对比表 |
| `--max-running-requests` | 8 | 同时处理几个请求。**这是吞吐量的真正阀门** |
| `--cuda-graph-max-bs` | 8 | 必须 ≥ 上面的值，否则批处理超过 8 会退化成慢路径 |
| `--speculative-num-draft-tokens` | 8 | 投机解码草稿长度。**这个值由草稿模型自己决定**（见踩坑 4） |
| KV 缓存精度 | fp8 | 把缓存内存直接砍半，质量损失可忽略 |
| `--sleep-on-idle` | 开启 | 空闲时休眠，否则空转一个 CPU 核、多耗 10–12W |

## 5. 调优结论：什么有用、什么没用

### ✅ 真正有用的

| 手段 | 效果 |
|---|---|
| **投机解码** | 单流速度提升 2–3 倍，**且不改变输出质量**（引擎会完整验证每个字） |
| **换成小模型** | 27B 比 176B **单流快 18%、并发快 130%**、省 150 GB 磁盘 |
| **下载走 ModelScope** | 部署时间从 3 小时压到 1 小时 |
| **fp8 KV 缓存** | 缓存内存砍半 |

### ❌ 试过但没用的（这些弯路值得记住）

| 想法 | 结果 |
|---|---|
| **加深投机草稿** | 176B 被 QSA 架构**硬性锁死在 4**；27B 的 8 是**草稿模型训练时的块大小**（`block_size: 8`），也不是保守取值 |
| **提高 mem-fraction 换速度** | **完全无效**。实测 KV 缓存峰值只用 **18%**——池子再大也用不上，而速度是带宽决定的，不是内存容量 |
| **切到纯命令行省资源换速度** | 实测桌面环境只占 **1.5–2 GiB**（121.6 GiB 的 1.3%），换算成 mem-fraction 只有 +1.6 个百分点。**对速度的直接收益接近于零** |
| **加更多并发** | 32 路请求相比 8 路只快 12%，但首字等待慢 50 倍。**亏本买卖** |

> **一句话总结**：这台机器上，**唯一还没验证过的提速空间是"放宽并发上限"**（同时改 `max-running-requests` 和 `cuda-graph-max-bs`），因为内存完全富余（KV 只用 18%）。这是下一步值得做的实验。

## 6. 踩坑合集（最有价值的部分）

### 坑 1：下载速度能决定项目成败

HuggingFace 直连只有 12.5 MB/s，ModelScope 有 40+ MB/s。**同样的文件、同样的校验，差 3 倍时间。**
办法：**用快的通道下载，用官方哈希校验**——速度和正确性都要。

### 坑 2：符号链接的层数写死会静默出错

我们把下载的文件用"软链接"接到 HuggingFace 的标准缓存结构上。链接路径写死成了 `../../blobs/xxx`。

- 根目录下的文件：✅ 正确
- **子目录下的文件：❌ 少一层，变成断链**

这个 bug 在 419 个文件全在根目录时**完全看不出来**，直到换了另一个模型、它有个 `assets/` 子目录才暴露。

**教训**：路径要用"相对当前位置计算"，不要写死层数。

### 坑 3：缓存判定逻辑会随版本变

不同版本的 `huggingface_hub` 判定"文件是否已缓存"的规则不同。老版本比对哈希，1.x 版本只看软链接是否存在。
**动手前先读源码确认**，否则可能白下载 135 GB。

### 坑 4：有些参数是"模型属性"，不是"引擎旋钮"

我们以为草稿长度 8 是"保守默认值，可以调大"。查了草稿模型的 `config.json` 才发现：

```json
"dflash_config": { "block_size": 8 }
```

**这是模型训练时就定死的**，调大没有意义。176B 那边同理——4 是引擎的架构限制。

**教训**：调参前先确认这个参数的**归属**——是引擎的、还是模型自带的。

### 坑 5：非法参数 10 分钟后才炸（最坑的一个）

投机解码的非法参数**不会在启动时报错**，而是在**权重加载完成约 10 分钟后**才抛异常。
而 systemd 配了"崩溃自动重启"，于是变成**每 10 分钟一轮的死亡循环**——看起来像"服务一直在重启"，很难第一眼看出是参数错。

**教训**：改这类参数前先 `systemctl stop`，改完再 `start`。

### 坑 6：中文的 token 密度是英文的 2 倍

实测：**中文 1.88 字符 = 1 个 token**；英文约 **4.5 字符 = 1 个 token**。

很多人（包括不少工具）用"字符数 ÷ 4"估算 token 数。**中文场景下这会低估约 2 倍**，导致你以为还有余量、实际已经超了。

### 坑 7：长会话换小窗口模型 = 必然失败

**现象**：`400 status code (no body)` + `CONTEXT_WINDOW_EXCEEDED`

**原因**：一个在 100 万窗口模型上跑了很久的会话，历史可能有 200 万 token 那么长。把它切到只有 26 万窗口的模型 → 引擎直接拒绝。

**注意**：**换模型要在会话早期做，或者新开会话**。这不是配置错误，是物理放不下。

### 坑 8：卸载脚本不删数据

很多项目的卸载脚本会删服务配置，但**从不碰数据**（权重、镜像、缓存），它会打印回收命令让你自己执行。
这是好设计（防误删），但你要知道**磁盘不会自动释放**。

### 坑 9：桌面环境比想象中省，但浏览器不省

实测整个 GNOME 桌面栈只占 **1.45 GiB**。但机器上开着的 **Firefox 单独占 270 MiB 显存 + 16.8% 的单核 CPU**。

**关掉浏览器比切换整个系统到命令行更划算。**

## 7. 日常运维手册

### 文件都在哪

| 用途 | 路径 |
|---|---|
| **实际启动命令** | `/etc/systemd/system/qwen38-sglang.service`（启动命令直接写在这个文件里） |
| 保活代理 | `/etc/systemd/system/qwen38-keepalive.service` |
| 配置与密钥目录 | `~/.config/qwen38/` |
| 模型权重 | `~/.cache/huggingface/hub/` |
| 安装脚本仓库 | `~/dsh-work/repo/` |

### 常用命令

```bash
# 看状态
systemctl status qwen38-sglang

# 看实时日志
journalctl -u qwen38-sglang -f

# 重启（约 6–9 分钟，耐心等）
sudo systemctl restart qwen38-sglang

# 健康检查
curl http://127.0.0.1:30000/health

# 调用模型
KEY=$(cat ~/.config/qwen38/api-key)
curl http://127.0.0.1:30000/v1/chat/completions \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.8-27b","messages":[{"role":"user","content":"你好"}]}'
```

### 端口说明

| 端口 | 用途 |
|---|---|
| 30000 | 引擎直连（OpenAI 兼容 + Anthropic 兼容） |
| 30001 | **保活代理**——Agent 类客户端（会长时间无输出）走这个，否则容易被超时断开 |

### 改参数的正确姿势

⚠️ **不要直接编辑那个 `.service` 文件**——下次跑安装脚本会被覆盖。应该改**传给安装脚本的环境变量**：

```bash
cd ~/dsh-work/repo
CONTEXT_MODE=1m ./install.sh        # 切换到 100 万上下文模式
```

## 8. 三条给后来者的建议

1. **先量带宽，再谈调优。** 这台机器的所有性能取舍都围绕 273 GB/s 这个带宽数字。任何"提高算力利用率"的思路在这里都是错的方向。

2. **调参前先确认参数归谁管。** 是引擎的旋钮？还是模型自带的属性？调错了不但没用，还可能让服务陷入崩溃循环。

3. **先测再信。** 网上（包括本文）的性能数字都依赖具体配置。同一台机器、同一份权重，换个参数就是另一个数字。**引用任何数字都要连配置一起引用。**
